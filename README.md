# FitCoach 运动建议

读取 Android **Health Connect** 中的运动数据（Google Fit、Fitbit、三星健康、Garmin 等都会同步到这里），
分析训练负荷和身体恢复情况，给出当天或第二天的建议：**加量 / 维持 / 减量 / 休息**，
并附上建议时长、心率区间、判断依据、一周计划和长期趋势。

> 为什么不用 Google Fit API：Google 从 2024 年起已弃用 Google Fit API，并要求开发者在 2026 年前迁移到 Health Connect。

## 功能

- **今日**：当天建议（时长、心率区间、理由）、肌肉恢复估算、恢复情况、28 天负荷图、早晨状态和训练疲劳度自评
- **本周**：周一到周日的训练安排（按训练目标分配有氧 / 力量日）与完成进度
- **力量**：记录动作、组数、次数、重量和整次 RPE；每个肌群每周的有效组数；各部位酸痛自评
- **训练目标**：减脂 / 增肌 / 保持健康，改变训练内容，不改变安全判断
- **趋势**：最近 12 周的每周负荷、急慢性负荷比、HRV、静息心率走势
- **每天 7:30 推送建议**（可选），后台同步最新数据
- **桌面小组件**：不用打开应用就能看到今天的建议
- 按年龄 / 性别个性化；生病前兆提醒；女性生理周期信息（仅供参考）

## 算法

1. **每日负荷**（Banister TRIMP）：`时长 × HRR × 0.64 × e^(1.92 × HRR)`，其中 HRR 是心率储备百分比。
   - 运动记录没有心率时：用户填了 RPE 就按 `HRR ≈ 0.3 + 0.06 × RPE` 换算（力量训练心率偏低，按心率会低估）；否则按中等强度 (HRR 0.6)；
   - 只有步数时，把超过 3000 步的部分折算成步行分钟，按低强度估算。
2. **急慢性负荷比 ACWR** = 急性负荷 ÷ 慢性负荷，两者都用**指数加权移动平均 (EWMA)** 计算
   （7 天 / 28 天，λ = 2/(N+1)；Williams et al., 2017），最多使用 56 天历史；最近 28 天至少需要 14 天有数据。
   | ACWR | 基础建议 |
   |---|---|
   | < 0.8 | 加量 |
   | 0.8 – 1.3 | 维持 |
   | 1.3 – 1.5 | 减量 |
   | > 1.5 | 减量（高风险） |
3. **恢复信号扣分**（中度 1 分，重度 2 分），扣 1–2 分降一档，3–4 分降两档，≥5 分直接休息：
   - **静息心率**：比基线（28 天中位数）高出个人阈值。阈值 = 2 × 稳健标准差（1.4826 × MAD），限制在 3–6 bpm；样本不足 10 天时用固定 5 bpm。重度阈值再加 3 bpm
   - **HRV**：近 7 天 lnRMSSD 均值相对个人基线（7 天之前的数据）的 z 分数，< −1 中度、< −2 重度；
     另外单日骤降（z < −2）记为中度。标准差下限 0.08，避免读数过于稳定时频繁误报
   - **睡眠**：昨晚不足 6h / 5h，或近 3 晚平均不足 6.5h；睡眠效率 < 85%（有睡眠分期数据时）
   - **训练模式**：连续训练 5 / 7 天以上；一周单调度 > 2；上一次训练量超过平时 1.6 倍；自评 RPE ≥ 9
   - **早晨自评**：很差（重度）/ 较差（中度）
4. **生病前兆**：体温 ≥ 37.5℃、夜间皮肤温度比基线高 ≥ 1℃，或静息心率连续 2 天以上偏高且 HRV 偏低 → 直接建议休息。
5. **目标量**：以"平时一次训练的负荷"为基准，加量 ×1.1、维持 ×1.0、减量 ×0.6，
   同时按 EWMA 模型解出"做完后 ACWR 不超过上限"的最大负荷作为封顶，再按心率区间换算成分钟数。
6. **按年龄 / 性别个性化**（用户在"修改资料"里填写，保存在本机）：
   | 条件 | 调整 |
   |---|---|
   | 填了实测最大心率 | 直接使用，优先于公式 |
   | 女性 | 最大心率用 Gulati 公式 `206 − 0.88 × 年龄`；TRIMP 用女性系数 `0.86 · e^(1.67x)`；显示生理周期第几天（不影响等级） |
   | 男性 / 未填写 | 最大心率用 Tanaka 公式 `208 − 0.7 × 年龄`；TRIMP 用 `0.64 · e^(1.92x)` |
   | ≥ 50 岁 | 加量幅度 10% → 5%；连续训练 4 / 6 天即提醒；每周至少休息 2 天 |
   | ≥ 65 岁 | ACWR 安全上限 1.3 → 1.2 |
   | < 18 岁 | 睡眠阈值各提高 1 小时（推荐 8–10 小时） |
7. **一周计划**：本周目标 = 慢性负荷 × 7 × 系数（由 ACWR 基础等级决定）；已过去的日子按实际负荷归类，
   今天沿用当天建议，剩余日子按"强弱交替、强度日后不接强度日、每周最多 2 个强度日、至少 1（50 岁以上 2）天休息"排布，
   再按权重分配剩余负荷（单日不超过平时的 1.5 倍）。

所有通用阈值都在 `EngineConfig` 里，可以调整。

## 设计说明：训练目标、力量训练记录、肌肉疲劳估算

三个功能互相衔接，但都**不改动安全层**：急慢性负荷比 (ACWR) 得出的等级、恢复信号的降档、生病时休息，
对所有目标完全一样。目标和肌肉疲劳只决定"今天练什么、怎么练"。

**1. 训练目标**（减脂 / 增肌 / 保持健康，在"修改资料"里选择，未选择时沿用原来的纯有氧建议）

| | 减脂 | 增肌 | 保持健康 |
|---|---|---|---|
| 主要方式 | 有氧为主 + 每周 2 次全身力量（保留肌肉） | 力量为主，有氧作为辅助 | 有氧 + 每周 2 次全身力量 |
| 强度分布 | 约 80% 低强度（Zone 2）/ 20% 较高强度 | 每组 6–12 次、RPE 7–9；有氧以轻松为主 | 以中等强度为主 |
| "加量"指什么 | 延长有氧时长、每天多走约 2000 步 | 每个动作加 1 组，或在次数做满后加 2.5–5% 重量 | 有氧多 5–10 分钟 |
| "减量"指什么 | 缩短时长、保留日常步行 | 每个动作少 1 组、RPE ≤ 7，重量不变 | 缩短时长、降低强度 |
| 一周计划 | 2 个全身力量日（间隔 ≥ 48 小时，避开强度日），其余为有氧 | 上下肢分化，每个肌群每周 2 次，同一肌群间隔 ≥ 48 小时 | 同减脂；并显示本周有氧分钟数对照 WHO 建议的 150–300 分钟 |

一周计划的强度日 / 休息日 / 负荷分配仍由原来的算法决定，目标只给每个训练日指定内容（有氧 / 上肢 / 下肢 / 全身力量）。

**2. 力量训练记录**（新的「力量」页）：记录动作、组数、次数、重量、时长和整次训练的 RPE，存在本机 JSON 文件。
- 心率会低估力量训练的负荷，所以负荷用 **session-RPE × 分钟**（Foster 法），
  再通过已有的 `TrainingLoad.hrrFromRpe` 换算到 TRIMP 尺度（`分钟 × TRIMP/分钟(HRR(RPE))`），直接进入 ACWR 模型；
- 某天有力量记录时，Health Connect 里同一天的"力量训练"类运动会被替换，避免重复计算；
- 每周**有效组数**按肌群统计：主要发力肌群算 1 组、协同肌群算 0.5 组；整次 RPE ≤ 3 的热身/技术练习不计。
  每个肌群每周约 10–20 组是常用的有效区间。

**3. 肌肉疲劳估算**（启发式模型，界面上全部标注"估算"——目前没有经过验证的可穿戴设备指标能测量单个肌群的疲劳）
- 动作 → 肌群权重表（主要肌群 1.0、协同 0.5、辅助 0.25）；Health Connect 的跑步、骑行、游泳、划船、椭圆机、徒步/爬楼、步行也有各自的肌群权重；
- 每次训练给每个肌群一个"剂量"（单位：相当于多少个力竭组）：力量 = 组数 × 权重 × 相对强度（由 RPE 换算，RPE 8 = 1.0）；
  有氧 = 小时数 × 强度（HRR / 0.7）× 权重 × 6；
- 疲劳按指数衰减：`疲劳 = Σ 剂量 × e^(−经过小时 / τ)`，大肌群 τ ≈ 30 小时，小肌群约 20 小时；10 组剂量视为完全疲劳，恢复度 = 1 − 疲劳 / 10；
- **酸痛自评**（各部位 0–10）用来校准：① 最近 36 小时内的自评按权重与模型结果融合；
  ② 积累几次自评后，为每个肌群拟合一个恢复时间系数（τ × 0.6–1.6，样本少时向 1 收缩），恢复快的人系数会变小；
  训练后 12 小时内的自评不用于拟合（延迟性酸痛还没出现）；
- 今日页显示各肌群恢复度；主要肌群恢复不足 70% 时，建议避开（例如"股四头肌约恢复 60%：今天练上肢"），
  两侧都不足时只建议轻松有氧或休息。

## 数据同步

- **首次**：完整导入最近 30 天，存到本机缓存，同时向 Health Connect 要一个"变更令牌"。
- **之后**：用令牌询问"上次之后哪些记录新增 / 修改 / 删除了"（Health Connect Changes API），
  只重新读取受影响的日期；最近两天总是重读一次（手表数据常有延迟）。
- **不重复**：每日数据以日期为键、运动记录以 Health Connect 记录 id 为键；更新时整段替换该日期区间，
  所以重复同步、中途中断都不会累加出重复数据。
- **自动回退到完整导入**：令牌过期（超过 30 天没打开）、授权变化、缓存文件损坏，或用户点"完整重新导入"。
  完整导入只替换最近 30 天，更早的历史会保留。
- **其他提速**：各类数据并行读取；运动平均心率查询结果会缓存，记录没改就不再重复查询；
  打开 app 时先用缓存立即显示结果，再在后台同步。
- 缓存最多保留 180 天，因此会逐渐积累超过 Health Connect 默认 30 天读取限制的历史。
- **后台同步**：每天早上的任务需要 Health Connect 的"在后台读取"权限（授权页里单独勾选，部分旧版本不支持）；
  没有该权限时使用上次打开应用时同步的数据。

## 开发

需要 JDK 17 或 21（Gradle 8.11 还不支持 JDK 25，Android Studio 新版自带的 JBR 25 不能直接用于命令行构建）。

```bash
./gradlew :engine:test
```

```bash
./gradlew testDebugUnitTest
```

```bash
./gradlew assembleDebug
```

每次推送到 GitHub 时，CI（`.github/workflows/ci.yml`）会自动跑引擎测试、应用单元测试、Lint，
并把调试版 APK 作为构建产物上传。

**Android 应用**：用 Android Studio 打开项目根目录，等 Gradle 同步完成后运行到手机或模拟器上。
- 需要 Android 8.0+；Android 14 及以上系统自带 Health Connect，更低版本需要从 Play 商店安装。
- 模拟器里通常没有健康数据，可以点页面底部的"演示场景"按钮查看效果。
